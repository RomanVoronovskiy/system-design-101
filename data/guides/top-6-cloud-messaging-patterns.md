Как сервисы взаимодействуют друг с другом? На схеме показаны шесть облачных шаблонов обмена сообщениями.

![](https://assets.bytebytego.com/diagrams/0378-top-6-cloud-messaging-patterns.png)

## Асинхронный запрос и ответ — Asynchronous Request-Reply

Шаблон делает взаимодействие с длительными фоновыми задачами предсказуемым и отделяет обработку на бэкенде от клиентов фронтенда.

На схеме клиент синхронно обращается к API и запускает длительную операцию на бэкенде. API возвращает код HTTP 202 (Accepted), подтверждая, что запрос получен и принят в обработку.

## Публикация и подписка — Publisher-Subscriber

Шаблон разделяет отправителей и потребителей сообщений. Отправитель не блокируется в ожидании ответа.

## Передача ссылки вместо сообщения — Claim Check

Шаблон решает проблему передачи больших сообщений. Полезная нагрузка целиком сохраняется в базе данных, а передаётся только ссылка на сообщение. По ней получатель затем извлекает данные из базы.

## Очередь с приоритетами — Priority Queue

Запросы к сервисам получают приоритеты. Более приоритетные запросы принимаются и обрабатываются раньше менее приоритетных.

## Сага — Saga

Сага помогает поддерживать согласованность данных между несколькими сервисами распределённой системы. Это особенно важно в микросервисной архитектуре, где каждый сервис управляет собственной базой данных.

Шаблон позволяет решать задачу согласованности без распределённых транзакций, которые сложно масштабировать и которые могут снижать производительность системы.

## Конкурирующие потребители — Competing Consumers

Несколько потребителей параллельно обрабатывают сообщения из одного канала. Сложная координация между ними не требуется. Однако этот шаблон не гарантирует порядок обработки сообщений.
