Разберём оба подхода на простом примере.

## Аутентификация на основе сессий

Сведения о сессии сохраняются в базе данных или специальном хранилище, а пользователю передаётся идентификатор сессии.

Это похоже на ситуацию, когда пассажиру выдают только номер билета, а все остальные сведения о перелёте хранятся в базе авиакомпании.

Порядок работы:

* Пользователь отправляет запрос на вход. Фронтенд передаёт его серверу.
* Сервер создаёт сессию с использованием секретного ключа и сохраняет её данные в хранилище сессий.
* Клиент получает cookie с уникальным идентификатором сессии.
* При следующем обращении браузер отправляет этот идентификатор вместе с запросом.
* Сервер определяет пользователя по идентификатору сессии.

## Аутентификация на основе JWT

В этом подходе сведения о сессии не сохраняются в отдельном хранилище: нужные данные находятся в самом токене.

Это похоже на билет, в котором указаны все сведения о перелёте, только в закодированном виде.

Порядок работы:

* Пользователь отправляет запрос на вход серверу.
* Сервер проверяет учётные данные и выпускает JWT, подписанный ключом. Хранилище сессий не используется.
* JWT передаётся клиенту в cookie или в теле ответа. У каждого варианта есть преимущества и недостатки; на схеме выбран вариант с cookie.
* При каждом следующем запросе браузер отправляет cookie с JWT.
* Сервер проверяет подпись JWT соответствующим ключом и извлекает сведения о пользователе.
