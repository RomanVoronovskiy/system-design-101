Как мы можем оптимизировать производительность при **загрузке больших файлов** в службу объектного хранилища, например S3?

Прежде чем ответить на этот вопрос, давайте посмотрим, почему нам необходимо оптимизировать этот процесс. Размер некоторых файлов может превышать несколько ГБ. Можно загрузить такой большой объектный файл напрямую, но это может занять много времени. Если сетевое соединение прервется в середине загрузки, нам придется начать все сначала. Лучшее решение — разрезать большой объект на более мелкие части и загрузить их независимо. После загрузки всех частей хранилище объектов заново собирает объект из частей. Этот процесс называется **многочастной загрузкой**.

На диаграмме выше показано, как работает многочастная загрузка:

1. Клиент вызывает объектное хранилище, чтобы инициировать многочастную загрузку.

2. Хранилище данных возвращает идентификатор загрузки, который однозначно идентифицирует загрузку.

3. Клиент разбивает большой файл на мелкие объекты и начинает загрузку. Предположим, размер файла составляет 1,6 ГБ, и клиент разбивает его на 8 частей, поэтому размер каждой части составляет 200 МБ. Клиент загружает первую часть в хранилище данных вместе с идентификатором загрузки, полученным на шаге 2.

4. Когда часть загружается, хранилище данных возвращает ETag, который по сути является контрольной суммой md5 этой части. Он используется для проверки многочастных загрузок.

5. После загрузки всех деталей клиент отправляет полный многочастный запрос на загрузку, который включает идентификатор загрузки, номера деталей и ETags.

6. Хранилище данных собирает объект из частей по номеру детали. Поскольку объект действительно большой, этот процесс может занять несколько минут. После завершения сборки он возвращает клиенту сообщение об успехе.
