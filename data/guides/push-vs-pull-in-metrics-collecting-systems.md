Существуют два способа сбора, выталкивания или толкания данных по метрикам. Это рутинная дискуссия о том, какой из них лучше, и нет четкого ответа. В этом посте мы взглянем на модель притяжения.

На рис. 1 показан сбор данных с помощью модели, используемой для притяжения к HTTP. У нас есть специальные метрические сборщики, которые периодически получают метрические значения из прогонных приложений.

При таком подходе для получения данных сборщику метрических данных необходимо знать полный перечень конечных точек обслуживания. Один из наивных подходов заключается в использовании файла для хранения информации DNS/IP по каждому конечному пункту обслуживания на метрическом коллекционере, серверах. Хотя идея проста, этот подход трудно поддерживать в условиях, когда серверы часто добавляются или удаляются, и мы хотим обеспечить, чтобы метрические коллекционеры не пропускали сбор метрик с новых серверов.

Хорошая новость заключается в том, что у нас есть надежное, масштабируемое и поддающееся поддержанию решение, доступное через сервисное открытие, предоставляемое Kubernetes, зоопарком и т.д., где услуги регистрируют их доступность и метрический коллектор могут быть уведомлены компонентом сервисного открытия всякий раз, когда изменяется перечень конечных точек. Находка сервиса содержит правила конфигурации, касающиеся времени и места сбора метрических показателей, как показано на рис. 2.

На диаграмме 3 подробно объясняется таранная модель.

### Подробности модели pull

*   Сборщик метрических данных получает метаданные конфигурации конечных точек обслуживания из сервисного Discovery. Метаданные включают интервалы, адреса IP, параметры временного выхода и ретриверов и т.д.

*   Сборник метрических данных осуществляет метрическую проверку через заранее определенную точку HTTP (например, /метрика). Для того чтобы раскрыть конечный пункт, к этой службе обычно необходимо добавить библиотеку клиентов. На диаграмме 3 услугами являются серверы Web.

*   В факультативном порядке регистратор метрических данных регистрирует уведомление об изменении в системе Service Discovery для получения обновленной информации в случае изменения конечных точек обслуживания. В качестве альтернативы сборщик метрических данных может периодически проводить опросы на предмет изменения конечных точек.
