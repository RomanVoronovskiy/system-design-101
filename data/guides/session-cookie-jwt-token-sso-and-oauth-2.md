После входа на сайт система должна учитывать, кто вы и какие действия вам доступны. Разные подходы устроены следующим образом:

* **Сессия:** сервер хранит сведения о пользователе и передаёт браузеру cookie с идентификатором сессии. Так он отслеживает состояние входа. Однако cookie неудобно использовать для переноса сессии между устройствами.
* **Токен:** сведения о пользователе кодируются в токене, который отправляется браузеру. Затем браузер передаёт его в запросах для аутентификации. Хранить серверную сессию не требуется. Токену нужна криптографическая защита; в зависимости от формата применяются подпись и/или шифрование.
* **JWT:** JSON Web Token задаёт стандартный формат токена. Цифровая подпись позволяет проверить его подлинность и целостность. Подпись содержится в самом токене, поэтому отдельная серверная сессия не обязательна.
* **SSO:** единый вход использует центральный сервис аутентификации. Одна процедура входа позволяет работать на нескольких сайтах.
* **OAuth 2.0:** позволяет предоставить одному сайту ограниченный доступ к данным на другом, не передавая пароль.
* **QR-код:** случайный токен кодируется в QR-коде для входа через мобильное устройство. Сканирование позволяет войти без набора пароля.

Примечание русской редакции: исходное утверждение об обязательном шифровании токенов уточнено. Подписанный JWT не обязательно зашифрован.
